# INC017 — systemd Service Crash and Core-Dump Backtrace

Status: **completed**

## Summary

A controlled fault was introduced into the systemd-managed `canonical-crash-demo.service` on Ubuntu host `p4-web-01`.

The service was healthy before the change. Setting `TRIGGER_CRASH=1` caused the Python process to invoke a deliberate native crash path through `ctypes`, producing a segmentation fault. systemd recorded the service failure as a core dump. `coredumpctl` and GDB were then used to inspect the native stack and correlate the failure with the expected `_ctypes` / `libffi` path.

The service was recovered by restoring `TRIGGER_CRASH=0` and restarting it. Recovery was validated through systemd state, process state, and application health logging.

## Environment

- Host: `p4-web-01`
- OS family: Ubuntu
- Service: `canonical-crash-demo.service`
- Runtime: `/usr/bin/python3`
- Debugger: GNU gdb 12.1
- Core manager: systemd-coredump / coredumpctl
- Crash PID: `12228`
- Recovery PID: `12277`

## Healthy baseline

Before failure injection:

```text
ActiveState=active
SubState=running
PID=12211
trigger_crash=0
health=ok
```

systemd reported the service as active and running.

## Failure injection

The environment file was changed from:

```text
TRIGGER_CRASH=0
```

to:

```text
TRIGGER_CRASH=1
```

The service was then restarted.

## Failure evidence

At **2026-09-18 12:41:17 UTC**, systemd reported:

```text
Active: failed (Result: core-dump)
Process: 12228 ... (code=dumped, signal=SEGV)
Main PID: 12228 (code=dumped, signal=SEGV)
```

The journal showed:

```text
canonical-crash-demo started pid=12228 trigger_crash=1
controlled failure injection: invoking native crash
canonical-crash-demo.service: Main process exited, code=dumped, status=11/SEGV
canonical-crash-demo.service: Failed with result 'core-dump'.
```

## Core-dump evidence

`coredumpctl info` identified:

```text
PID: 12228
Signal: 11 (SEGV)
Command Line: /usr/bin/python3 /opt/canonical-gap-lab/inc017_crash_service.py
Executable: /usr/bin/python3.10
Unit: canonical-crash-demo.service
Storage: /var/lib/systemd/coredump/...
```

The automatically decoded stack included:

```text
#0  __strlen_sse2
#1  _ctypes.cpython-310-x86_64-linux-gnu.so
#2  libffi.so.8
#3  libffi.so.8
#4  _ctypes.cpython-310-x86_64-linux-gnu.so
#5  _ctypes.cpython-310-x86_64-linux-gnu.so
#6  _PyObject_MakeTpCall
...
```

## GDB investigation

The core was opened with GDB.

GDB confirmed:

```text
Core was generated by '/usr/bin/python3 /opt/canonical-gap-lab/inc017_crash_service.py'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0 __strlen_sse2 ()
```

The backtrace again showed the native call chain passing through:

```text
__strlen_sse2
-> _ctypes
-> libffi
-> _ctypes
-> CPython evaluation frames
```

This matched the expected failure path from the controlled `ctypes.string_at(0)` invocation in the lab service.

## Root cause

The service was deliberately configured with `TRIGGER_CRASH=1`.

That configuration caused the Python process to execute a native `ctypes` call against address zero. The invalid native memory access propagated through `_ctypes` and `libffi`, terminating the process with SIGSEGV.

The root cause was therefore the controlled crash configuration, not an underlying systemd, kernel, resource, or networking failure.

## Remediation

The environment file was restored to:

```text
TRIGGER_CRASH=0
```

The service was then restarted.

## Recovery validation

At **2026-09-18 12:45:51 UTC**, the service returned to a healthy state.

Observed:

```text
ActiveState=active
SubState=running
Main PID: 12277
trigger_crash=0
health=ok
```

systemd reported:

```text
Active: active (running)
```

The journal showed continued health logging after recovery:

```text
canonical-crash-demo started pid=12277 trigger_crash=0
health=ok
health=ok
```

## Recovery time

## Troubleshooting workflow demonstrated

1. Establish healthy baseline
2. Introduce one controlled change
3. Confirm customer-visible/service failure
4. Inspect systemd state
5. Correlate journal timestamps
6. Identify the core dump
7. Inspect crash metadata with `coredumpctl`
8. Analyze native stack with GDB
9. Map stack evidence to the injected failure
10. Restore configuration
11. Restart service
12. Validate end-to-end recovery

## Conclusion

This incident demonstrates explicit Ubuntu crash troubleshooting beyond ordinary service restarts.

The investigation used systemd, journalctl, systemd-coredump, coredumpctl, and GDB to move from symptom to native crash evidence, identify the root cause, apply a minimal remediation, and validate recovery.

This was a controlled lab incident and not a customer production outage.
